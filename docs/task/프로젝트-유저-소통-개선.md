# 프로젝트 상세 소통 구조 개선안

## 문서 목적

이 문서는 `/project/[id]` 상세페이지를 단순 소개 화면이 아니라, **프로젝트 팀과 사용자가 자연스럽게 만나고 대화하며 다음 버전을 함께 만드는 소통 채널**로 재설계하기 위한 기준 문서입니다.

`docs/concept`의 핵심 방향은 명확합니다.

- 빠르게 만든다
- 빠르게 공개한다
- 빠르게 대화한다
- 빠르게 개선한다

따라서 프로젝트 상세페이지의 역할도 단순 랜딩이 아니라, **발견 이후의 관계 형성**까지 담당해야 합니다.

---

## 1. 문제 정의

현재 상세페이지는 프로젝트를 "보여주는" 데는 적합하지만, 사용자가 "말을 걸기"에는 불리합니다.

### 현재 핵심 문제

- `커뮤니티 참여` CTA가 추상적이라 사용자가 무엇을 할 수 있는지 즉시 이해하기 어렵다.
- 좋아요, 저장, 링크, 커뮤니티 등 여러 액션이 같은 무게로 배치되어 우선순위가 흐려진다.
- 탭 구조가 정보 탐색 중심이라 질문, 요청, 의견 제안 같은 소통 행동을 유도하지 못한다.
- 팀의 응답 온도, 반영 속도, 해결 이력 같은 신뢰 신호가 약하다.
- 공식 업데이트 외에 프로젝트 관리자가 가볍게 생각이나 고민을 공유할 공간이 부족하다.

### 결과적으로 생기는 UX 손실

- 사용자는 "어디에 어떤 방식으로 의견을 남겨야 하는지" 확신이 없다.
- 팀은 의견을 받아도 구조적으로 정리되지 않아 운영 부담이 커진다.
- 프로젝트는 살아 있는 제품이 아니라 정적인 소개 페이지처럼 보인다.

---

## 2. 관점별 설계 원칙

이 개선안은 `UI/UX 설계자`, `미니멀리스트 디자이너`, `소통 및 심리학 전문가`의 관점을 동시에 반영합니다.

### 2.1 UI/UX 설계자 관점

상세페이지의 1순위 과업은 "프로젝트 이해"가 아니라, **프로젝트 이해 후 즉시 참여할 수 있게 만드는 것**입니다.

따라서 UI/UX는 아래 원칙을 따라야 합니다.

- 첫 화면에서 사용자의 다음 행동이 하나로 보이게 한다.
- 정보 탐색보다 행동 진입을 먼저 설계한다.
- 피드백, 질문, 요청, 업데이트를 분리하되 서로 연결되게 만든다.
- 팀 기능과 사용자 기능을 섞지 않고 역할 기반으로 나눈다.
- 모바일에서도 동일한 참여 경험이 유지되도록 입력 진입을 짧게 만든다.

### 2.2 미니멀리스트 디자이너 관점

미니멀리즘은 요소를 줄이는 것이 아니라, **의미가 겹치는 요소를 제거해 핵심 행동을 선명하게 만드는 것**입니다.

따라서 화면은 아래처럼 정리되어야 합니다.

- 상단에는 프로젝트 정체성, 신뢰 신호, 핵심 CTA만 남긴다.
- 보조 액션(좋아요, 저장, 링크)은 시각적 우선순위를 낮춘다.
- 탭 수는 많더라도 역할이 겹치지 않게 정의한다.
- 카드, 뱃지, 필터는 많아 보여도 정보 구조가 단순해야 한다.
- "무엇을 할 수 있는지"보다 "지금 무엇을 하면 되는지"가 먼저 보여야 한다.

### 2.3 소통 및 심리학 관점

사람은 의견을 남길 때 두 가지를 먼저 판단합니다.

1. 여기서 말해도 안전한가
2. 말하면 실제로 반응이 오는가

따라서 소통 UX는 아래 심리 원칙을 만족해야 합니다.

- 심리적 안전감: 비난보다 질문과 제안을 유도하는 톤
- 응답 예측 가능성: 답변 시간, 상태 변화, 반영 이력 노출
- 낮은 참여 마찰: 한 번의 클릭으로 작성 유형 선택 가능
- 기여 효능감: 내 의견이 업데이트와 연결되는 경험 제공
- 관계감 형성: 공식 공지 외에도 팀의 인간적인 온도를 보여주는 채널 필요

## 3. 목표 재정의

### 제품 목표

1. 사용자가 10초 안에 "이 프로젝트 팀과 어떻게 대화할 수 있는지" 이해한다.
2. 팀이 사용자 의견을 구조적으로 받고, 공개적으로 응답하며, 반영 과정을 보여줄 수 있다.
3. 상세페이지가 소개, 대화, 우선순위 정리, 결과 공유를 모두 연결하는 허브가 된다.

### UX 목표

- 첫 참여까지의 흐름을 `상세 진입 -> 유형 선택 -> 작성`으로 단순화
- 사용자 관점과 관리자 관점을 같은 화면 안에서 역할별로 분리
- 모바일에서 스크롤 중에도 언제든 참여할 수 있게 CTA를 유지

### 핵심 지표

- 상세 방문 대비 첫 의견 작성 전환율
- 팀 첫 응답까지의 중앙값 시간
- 팀 노트 조회 대비 반응 전환율
- 요청 생성 후 상태 변경 비율
- 사용자 의견이 업데이트에 연결된 비율
- 7일 재방문율

---

## 4. 핵심 설계 방향

프로젝트 상세는 하나의 커뮤니티가 아니라, 역할이 다른 세 개의 채널을 가진 구조가 되어야 합니다.

### 채널 1. 대화

질문, 짧은 의견, 가벼운 반응이 오가는 열린 대화 공간입니다.

### 채널 2. 요청 보드

버그, 기능 요청, 개선 아이디어처럼 우선순위와 상태 관리가 필요한 구조화된 공간입니다.

### 채널 3. 팀 노트

공식 업데이트보다 가볍고 빠른 톤으로 팀의 고민, 의견, 질문, 근황을 공유하는 공간입니다.

### 채널 4. 업데이트

결정과 반영 결과를 남기는 공식 채널입니다.  
즉, `대화와 팀 노트`가 입력이라면, `업데이트`는 결과 보고 채널입니다.

## 5. 정보 구조(IA) 제안

### 상단 Hero의 역할

상단은 "이 프로젝트가 무엇인가"를 보여주는 동시에, "지금 어떻게 참여할 수 있는가"를 명확히 알려야 합니다.

### Hero 필수 요소

- 프로젝트명
- 한 줄 소개
- 대표 링크 (`웹사이트`, `데모`, `저장소` 등)
- 핵심 신뢰 지표
  - 최근 답변 시간
  - 최근 30일 응답률
  - 해결/반영 건수
- 1차 CTA: `의견 남기기`
- 2차 CTA: `요청 보드 보기`
- 보조 CTA: `팀 노트 보기`

### 보조 액션 정리

- `좋아요`, `저장`, `링크 공유`는 유지하되 시각적 비중을 낮춘다.
- 사용자의 주 행동은 소비가 아니라 참여이므로, 보조 액션이 핵심 CTA를 이기면 안 된다.

## 6. 탭 구조 제안

### 권장 탭 순서

1. `대화`
2. `요청 보드`
3. `팀 노트`
4. `업데이트`
5. `개요`
6. `팀`
7. `갤러리` (필요 시)

### 왜 이 순서인가

- 사용자는 먼저 사람과 대화할 수 있어야 한다.
- 그 다음에는 요청을 구조적으로 볼 수 있어야 한다.
- 그 다음에야 팀의 맥락과 결과물을 읽게 된다.

즉, 상세페이지의 흐름은 `정보 이해 -> 소통`이 아니라,  
`관심 형성 -> 대화 -> 신뢰 형성 -> 더 깊은 이해`가 되어야 합니다.

---

## 7. 탭별 설계

### 7.1 대화 탭

가장 접근성이 높은 참여 공간입니다. "말을 걸기 가장 쉬운 곳"이어야 합니다.

#### 구성

- 상단 빠른 작성 박스
- 유형 칩
  - `질문`
  - `버그 제보`
  - `기능 요청`
  - `개선 아이디어`
  - `자유 의견`
- 정렬
  - `최신순`
  - `답변 필요`
  - `인기순`
- 필터
  - `팀 답변 있음`
  - `미답변`
  - `해결됨`

#### 심리적 이유

- 사용자는 빈 입력창보다 "유형이 있는 입력창"에서 훨씬 쉽게 말을 시작한다.
- 질문, 요청, 아이디어를 먼저 제시하면 참여의 언어를 플랫폼이 제공하게 된다.

#### 카드 정보

- 제목 또는 첫 문장
- 작성자/시간
- 유형
- 상태
- 팀 답변 여부
- 공감 수 / 댓글 수

### 7.2 요청 보드 탭

대화를 구조적 자산으로 바꾸는 공간입니다.

#### 상태 구조

- `접수`
- `검토중`
- `진행중`
- `출시됨`
- `보류`
- `중복 병합`

#### 핵심 규칙

- 요청 작성 시 유사 요청 자동 추천
- 중복 요청은 병합 가능
- `출시됨` 상태는 반드시 업데이트와 연결
- 팀이 상태를 바꾸면 짧은 코멘트가 남아야 함

#### 심리적 이유

- 상태 변화는 단순 운영 기능이 아니라 "내 의견이 사라지지 않았다"는 신호다.
- 사용자는 해결 자체보다, 검토가 시작되었다는 사실만으로도 신뢰를 느낀다.

### 7.3 팀 노트 탭

관리자와 팀이 가볍게 생각을 공유하는 소통 레이어입니다.  
이 탭은 공식성보다 친밀도와 맥락 전달이 중요합니다.

#### 팀 노트의 존재 이유

- 공식 업데이트는 결과 중심이라 자주 쓰기 어렵다.
- 사용자는 완성된 답보다 진행 중인 고민을 더 흥미롭게 느낀다.
- 프로젝트 팀의 목소리가 보이면 브랜드보다 사람이 보이고, 이는 참여 장벽을 낮춘다.

#### 적합한 콘텐츠

- 우선순위 고민
- 이번 주 작업 방향
- 사용자에게 묻는 질문
- 반응이 궁금한 디자인/기능 선택지
- 가벼운 회고

#### 예시

- `검색 개선과 저장 기능 중 무엇이 더 급할까요?`
- `온보딩 첫 화면이 너무 길다는 의견이 있었는데, 여러분은 어땠나요?`
- `이번 주는 버그 수습 주간입니다. 가장 거슬리는 문제를 알려주세요.`

#### 상호작용

- 공감
- 짧은 댓글
- 투표
- 요청 보드로 승격

#### 운영 규칙

- 작성 권한은 프로젝트 관리자/팀
- 주 2~3회 이내 권장
- 가벼운 글은 일정 기간 후 아카이브 가능
- 상단 고정은 1건만 허용

### 7.4 업데이트 탭

업데이트는 "무엇이 바뀌었는가"를 말하는 공식 채널입니다.

#### 포함 정보

- 변경 내용
- 왜 바뀌었는지
- 어떤 요청/대화/팀 노트에서 출발했는지
- 영향 범위
- 다음 계획

#### 심리적 이유

- 사용자는 업데이트 자체보다, 자신의 참여가 결과에 닿았는지에 더 민감하다.
- 따라서 업데이트는 단독 콘텐츠가 아니라 이전 대화와 연결되어야 한다.

### 7.5 개요 탭

개요는 여전히 필요하지만, 더 이상 첫 번째 탭일 필요는 없습니다.

#### 역할

- 프로젝트 설명
- 주요 기능
- 기술 스택
- 데모 사용 가이드
- 알려진 제한사항

### 7.6 팀 탭

팀 탭은 단순 프로필이 아니라 "누가 답변하는가"를 보여줘야 합니다.

#### 포함 정보

- 팀원 이름/역할
- 응답 담당 배지
- 평균 응답 시간
- 활동 시간대
- 운영 정책 요약

## 8. 레이아웃 설계

### 데스크톱

- 좌측 메인 컬럼: 현재 탭 콘텐츠
- 우측 사이드 패널:
  - `의견 남기기`
  - 응답 신뢰 지표
  - 최근 해결된 요청
  - 팀 노트 하이라이트

### 모바일

- 상단에는 프로젝트 정체성과 핵심 CTA만 유지
- 좋아요, 저장, 공유는 보조 영역으로 내림
- 하단 고정 CTA 또는 FAB 제공
  - `의견 남기기`
  - 유형 선택 바텀시트

### 미니멀 관점의 주의점

- 한 화면에서 버튼이 3개를 넘으면 우선순위가 깨진다.
- 아이콘 액션은 남겨도 되지만, 레이블 있는 메인 CTA보다 눈에 띄면 안 된다.
- 카드 밀도는 높일 수 있지만, 행동 버튼은 반복적으로 과다 노출하지 않는다.

## 9. 인터랙션 및 카피 원칙

### CTA 원칙

- 추상 명사보다 행동 동사를 쓴다.
- "참여"보다 "질문하기", "의견 남기기", "요청하기"가 더 낫다.

### 권장 문구

- `팀과 대화 시작하기`
- `불편한 점 알려주기`
- `기능 요청 남기기`
- `팀의 고민 보기`

### 빈 상태 카피

- `첫 질문을 남겨보세요. 팀이 답변을 시작할 수 있습니다.`
- `아직 등록된 요청이 없습니다. 가장 불편한 점부터 알려주세요.`
- `팀이 고민을 공유하면 여기서 볼 수 있습니다.`

### 심리적 효과

- 명령형보다 초대형 문구가 더 부드럽다.
- 평가를 요청하는 문구보다 도움을 요청하는 문구가 참여율이 높다.
- "당신의 의견이 반영될 수 있다"는 메시지는 기여 효능감을 높인다.

## 10. 관리자 기능과 사용자 기능 분리

같은 화면 안에서 관리자 메뉴가 과도하게 드러나면, 사용자는 이 공간을 "내가 참여하는 곳"이 아니라 "관리자가 운영하는 곳"으로 느낍니다.

### 사용자 액션

- 질문 작성
- 버그 제보
- 기능 요청
- 개선 아이디어 제안
- 팀 노트 반응
- 프로젝트 구독

### 관리자/팀 액션

- 요청 상태 변경
- 공식 답변 등록
- 팀 노트 작성
- 업데이트 게시
- 요청 병합
- 팀 노트에서 요청으로 승격

### 원칙

- 관리자 액션은 더보기 또는 전용 편집 모드로 숨긴다.
- 사용자가 보는 기본 상태는 "참여 가능한 공간"이어야 한다.

## 11. 운영 정책

### 기본 응답 정책

- 신규 대화/요청은 24시간 이내 1차 응답 권장
- 요청은 7일 이내 상태 분류
- `보류`와 `중복`은 사유를 남김

### 팀 노트 운영 정책

- 팀 노트는 친밀한 톤을 허용하되, 공지와 혼동되지 않게 시각적으로 구분
- 질문형, 선택형, 회고형 템플릿 제공
- 운영 목적 없는 잡담형 포스트는 지양

### 모더레이션 정책

- 비방, 광고, 개인정보 노출 대응 기준 명시
- 사용자의 부정적 의견도 가능한 한 삭제보다 응답으로 처리

## 12. 단계별 실행 로드맵

### Phase 1

- Hero CTA 재구성
- `대화` 탭 기본화

- 팀 노트 최소 기능 도입

### Phase 2

- 요청 보드 상태 관리
- 중복 병합

- 팀 역할 배지
- 팀 노트에서 요청 승격

### Phase 3

- 개인화된 작성 템플릿
- 소통 건강도 점수
- 프로젝트 구독/알림 강화
- 팀 노트 기반 가벼운 설문/투표 고도화

### 정성 지표

- 사용자가 "어디서 말해야 할지 알겠다"고 느끼는가
- 팀이 "의견을 운영 가능한 형태로 받는다"고 느끼는가
- 상세페이지가 살아 있는 제품 공간처럼 보이는가

## 14. 최종 제안

핵심은 커뮤니티 기능을 더하는 것이 아니라, 프로젝트 상세의 성격을 **홍보 페이지에서 소통 운영 페이지로 전환**하는 것입니다.

이를 위해 가장 중요한 변화는 다섯 가지입니다.

1. `대화`를 기본 탭으로 둔다.
2. `요청 보드`를 별도 구조로 분리한다.
3. `팀 노트`를 통해 팀의 가벼운 목소리를 드러낸다.
4. `업데이트`를 결과 보고 채널로 재정의한다.
5. 상단에서 소통 CTA와 신뢰 지표를 가장 먼저 보여준다.

이 다섯 가지가 적용되면, 사용자는 이 페이지를 "읽고 나가는 곳"이 아니라, **말을 걸고 다시 돌아오는 곳**으로 인식하게 됩니다.
