# Task 03. 요청 보드와 구조화 피드백 설계

## 목적

가벼운 대화를 운영 가능한 요청 자산으로 전환하고, 사용자 의견이 사라지지 않는 구조를 만든다.

---

## 범위

- `요청 보드` 탭
- 상태 체계
- 중복 병합
- 요청 작성 템플릿
- 업데이트 연결 구조

---

## 설계 원칙

### 원칙 1. 요청은 댓글이 아니라 자산이어야 한다

#### 필요한 콘셉

- 기능 요청과 버그 제보는 반응형 콘텐츠가 아니라 운영 대상이다.
- 따라서 대화와 분리된 구조가 필요하다.

#### 필요한 아이디어

- `요청 보드` 별도 탭
- 요청 카드 단위 관리
- 상태 변경 이력 보존

#### 개선 항목

- 기능 요청/버그/개선 제안을 요청 모델로 구조화
- 댓글 흐름과 별도 상태 필드 설계
- 요청 단위 URL 또는 상세 진입 구조 검토

### 원칙 2. 상태는 신뢰 신호다

#### 필요한 콘셉

- 사용자는 해결보다도 "검토되고 있다"는 사실에서 신뢰를 얻는다.
- 상태는 내부 관리용이 아니라 외부 커뮤니케이션 장치다.

#### 필요한 아이디어

- `접수`
- `검토중`
- `진행중`
- `출시됨`
- `보류`
- `중복 병합`

#### 개선 항목

- 상태 변경 시 짧은 설명 코멘트 의무화
- 상태 필터/정렬 제공
- `출시됨`은 업데이트 문서와 자동 연결

### 원칙 3. 요청 작성의 마찰을 줄여야 한다

#### 필요한 콘셉

- 자유 서술은 부담이 크고, 정보 품질도 불안정하다.
- 필요한 정보를 템플릿이 대신 구조화해야 한다.

#### 필요한 아이디어

- 문제 설명
- 기대 행동
- 재현 방법
- 참고 화면/조건

#### 개선 항목

- 요청 유형별 작성 템플릿 제공
- 버그일 때만 재현 단계 필드 노출
- 모바일에서 짧은 입력으로도 등록 가능하게 설계

### 원칙 4. 중복은 통제 대상이지 실패가 아니다

#### 필요한 콘셉

- 비슷한 요청이 많다는 것은 수요가 높다는 뜻이기도 하다.
- 중복을 막기보다 모아주는 UX가 필요하다.

#### 필요한 아이디어

- 유사 요청 추천
- 중복 병합
- 병합 후 지지 수 통합

#### 개선 항목

- 작성 중 유사 요청 자동 추천
- 병합된 요청으로 사용자 이동 안내
- 병합 시 기존 참여 기록이 사라지지 않도록 설계

---

## 완료 기준

- 요청은 대화와 구분된 구조로 노출된다.
- 상태 변화만 봐도 운영 진행도가 이해된다.
- 중복 요청이 분산되지 않고 합쳐질 수 있다.
- 사용자는 요청을 남긴 뒤 추적 가능한 기대를 갖게 된다.
